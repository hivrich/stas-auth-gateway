## Живые проверки договора Intervals

Проверен реальный authorize-запрос формы ChatGPT без завершения входа:
gateway ответил 302, сохранил challenge/S256 и направил на правильный callback.
Публичный app-for-auth Intervals ответил 200: приложение STAS APPROVED,
publicClient=false, pkceRequired=false. Публичный текущий клиент Intervals
index-C3uTTJyS.js загружает OAuthAuthorizePage-CuPk9vAi.js; проверено, что
его обработчик согласия передаёт code_challenge/code_challenge_method в
/api/oauth/authorize. Это ничего не доказывает о версии клиента Kevin.

Один запрос к настоящему token endpoint со случайным заведомо несуществующим
кодом и штатными реквизитами приложения получил HTTP 400. Нового разрешения
пользователя такой запрос создать не может. Фактическое поле error:
`Code not found (expired?) or code_verifier does not match`.
Поля error_description в ответе не было. Это специально отрицательный тест,
а не восстановленный ответ на попытку Kevin.

Таким образом, Intervals использует и свободный текст в error; только список
стандартных OAuth-кодов недостаточен. В диагностике добавлено точное
сопоставление этой известной строки с code_or_pkce_rejected; исходная строка
не логируется. Diagnostics-тест дополнен настоящей формой ответа и прошёл.
Категория намеренно не разделяет неизвестный/истёкший код и неверный verifier:
сам Intervals объединяет эти причины в этом сообщении.

Владелец явно разрешил настоящий тест на своём аккаунте. Создан отдельный
подписанный клиент без refresh-доступа, с MCP scope ACTIVITY:READ.
Первый вручную подготовленный переход закончился invalid_state: его state
истёк в 18:46:27 UTC, а возврат был получен после 20:17 UTC. Gateway не
перезапускался. Это ошибка организации теста, не воспроизведение Kevin.
Исправлена тестовая ссылка: state создаётся штатным gateway только при её
открытии владельцем, а не заранее оператором.

Полный живой тест 27 октября в 20:19 UTC прошёл на аккаунте владельца:

## Независимая модель провайдера

Добавлен test-oauth-provider-contract.js: независимая модель провайдера
с проверкой исходного кода, заранее известного client_id/секрета/callback,
динамического SHA-256, срока действия и однократности кода. Для ChatGPT
используются его форма метаданных и private_key_jwt; для Claude — DCR с none.
18 проверок включают:

- Успешный обмен с verifier длиной 43, 64, 96 и 128 символов.
- Перекрывающиеся независимые попытки с разными кодами и verifier.
- Неверный verifier: отказ до Intervals, последующий правильный запрос успешен.
- Одновременный обмен одним кодом: ровно один запрос в Intervals.
- Просроченный upstream-код и отказ при его повторном обмене.
- Явно синтетическую потерю challenge на стороне модели провайдера.

Последние два сценария дают одинаковую старую запись upstream_rejected.
Они доказывают неоднозначность диагностики; **потеря challenge в настоящем
Intervals не наблюдалась и причиной инцидента не объявляется**.

Сроки действительно различаются: мост держит код 10 минут, тогда как
[документация автора Intervals](https://forum.intervals.icu/t/intervals-icu-oauth-support/2759)
требует обмен за 2 минуты. Тест двигает только часы модели провайдера;
часы моста не подменяются. Это воспроизводимый случай отказа при задержке,
но связь с ошибкой Kevin не установлена.

Запуск новых проверок из этой рабочей копии, используя уже установленные
зависимости основной копии:

```sh
env -i PATH="$PATH" \
  NODE_PATH=/home/codex/codex-work/Projects/stas-auth-gateway-clean/node_modules \
  node scripts/test-oauth-provider-contract.js
```

Новый тест разрешает реальные HTTP только своему локальному серверу;
все обращения к провайдеру и STAS моделируются, другие URL запрещены.
Это локальная проверка договора обмена, не настоящий вход аккаунтом Kevin.

## Подготовленная диагностика и оставшаяся работа

Сейчас ответ Intervals отдаётся клиенту, но его код причины не сохраняется.
Подготовлено добавление поля upstream_error из фиксированного списка
стандартных OAuth-ошибок и точного известного ответа настоящего Intervals.
Неизвестные строки, объекты и отсутствующие значения
становятся unrecognized. error_description и тело ответа не логируются.
Тесты проверяют категории, отсутствие секретов и сохранение прежних HTTP-ответов.
Это не исправление входа и даже после выпуска не всегда даст первопричину:
например, invalid_grant объединяет несколько возможных причин.

Стоимость Intervals: **0 дополнительных HTTP-запросов**. Кэш, повторы,
приоритеты, обработка истории, wellness и pipeline тренировок не меняются.
Схема БД, зависимости и настройки авторизации не меняются.

Публичные запросы без токена initialize и tools/list получили ожидаемый
HTTP 401 с WWW-Authenticate. Это проверка требования входа, а не успешного
подключения к данным пользователя.

Отсутствующий в старых журналах ответ задним числом получить нельзя.
Разрешённый владельцем контролируемый вход выполнен успешно; настоящий
отказ Kevin пока не захвачен. Для дальнейшего вывода нужен ответ Intervals
именно при неудачной попытке: через отдельно разрешённый выпуск безопасной
диагностики либо контролируемую неудачную попытку на стороне клиента.
Выпуск диагностики сам по себе не обещает установить первопричину.
Повторные попытки Kevin не запрашивались и сообщение ему не отправлялось.
